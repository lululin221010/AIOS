# 共用資產倉庫 v0.1

## 這是什麼

解決「創意在聊天室裡被丟掉」的問題：妹丟進來的案例（一支影片、一個梗、一種玩法、一個工具技巧），過去只活在那次對話裡，聊天室關掉就找不回來。倉庫的核心循環：**發現 → 收進來 → 整理 → 做東西時叫得出來 → 實際使用 → 看結果 → 結果回填倉庫**。

**v0.1的目標只有三件事，不追求完整系統或漂亮架構**（2026-09-23策/妹明確定案的驗收標準）：
1. 最近丟進來的素材（廣西怪地名、貓咪輪唱、101冷知識、VTuber工具箱、歌曲重新賦義、梗的變體樹……）能不能被收進去
2. 之後能不能找回來
3. 需要做社群內容時，能不能重新組合出具體東西

這三件事在下面用**真實素材**示範過一次（見「示範」章節），不是空的架構圖。

## 為什麼不是資料庫/向量搜尋（現在還不是）

09-19需求規格要求「10年後仍要準確找回」「支援語意搜尋」，這是v1+的目標，v0.1刻意不做，理由：
- 現在entries數量是個位數到幾十筆，CC自己讀完全部entries就能做語意判斷（人腦/AI推理本身就是最好的語意搜尋，不需要先蓋向量資料庫）
- 目前資料量不足以合理化額外架構成本——過早蓋資料庫是「先蓋工廠再等原料」
- **量大到CC讀不完全部entries時**（估計數百筆以上），才是真正該升級成SQLite FTS5或向量搜尋的時機點，那時再做，不是現在預先蓋好

每個entry是一份獨立markdown，YAML frontmatter記metadata，body記機制/來源/延伸方向/使用紀錄。**存的是「機制」不是原作品本身**（09-19已定案的迴避著作權原則：看到「貓跳舞配舞女」，存的是「歌曲辨識度+代表動作，觀眾不用解釋就懂」這個機制，不是那支影片）。

## 入庫判定（沿用09-19三分類＋09-21兩層過濾）

- **收**：跨時間跨任務可再利用、提供新觀點/方法/案例、難以重新取得、能避免重做/踩坑、與既有資產不重複
- **暫存**：現在看不出長期價值但不到丟——v0.1暫不建這一層，量小時直接判斷收或不收即可，等有真的拿不準的案例再開資料夾
- **不收**：純當次資訊、重複、無再利用價值——留在原聊天室，不特別記錄
- **妹保留強制收的否決權**：AI判不用但妹說要留，就進，寫entry時標註「妹指定保留」

兩層過濾（09-21「怪畫面解釋法」對話定案）：CC先用固定標準擋（新鮮感/記憶點/是否換皮/跟SS氣質合不合/事實正確/製作成本），妹的個人口味只用在CC判斷不出「這是不是妳的菜」的案例，不用每則都問妹。

## 動態淘汰（v0.1先記規則，還不自動執行）

entry放了一段時間（暫定2個月，之後可調）完全沒被使用（`used_count`仍是0），CC下次整理倉庫時要主動提出「這幾則要不要降級/淘汰」，不是讓妹自己發現。v0.1這步驟靠CC手動掃描entries的`used_count`欄位，不是排程自動化。

## 示範：三件事真的跑一次

### ① 收進去
下面`entries/`裡的6則，是從2026-09-21~23策的「0921」專案對話（見AIOS `01_Company/Active_Threads_Board.md`第4條）、以及09-19倉庫需求討論裡策順手提到的補充案例中，真的抽出機制寫成entry的（不是虛構測試資料）。

### ② 找回來
用`grep -rl "驚喜" 04_Systems/Warehouse/entries/`能找到W0001；用`grep -rl "貓" 04_Systems/Warehouse/entries/`能找到W0002；就算不知道確切用詞，CC讀完全部6則（現在量小，幾秒鐘的事）也能回答「有沒有看過機器人做很荒謬的事」這類意圖型查詢——這是09-19規格明確要求的能力，v0.1用「CC直接讀全部」滿足它，不用真的搜尋引擎。

### ③ 重新組合出東西
**情境**：假設妹說「SS明天想發一則跟魯魯有關的東西，沒有靈感」。

CC讀倉庫，挑出W0001（連續驚喜結構）+ W0004（VTuber工具箱：真貓/虛擬雙重狀態），組合提案：

> 拍一段魯魯日常（真貓，睡覺/理毛/任何真實反應），配文用「連續開盲盒」結構寫：第一句正常描述魯魯在幹嘛→第二句丟一個關於魯魯的冷知識或怪習慣→第三句更荒謬的聯想（例如「這隻貓可能覺得自己是CEO」）→留一個開放式問句勾第二天回訪（呼應09-22SS展場模式「回訪理由」篩選器）。不用真的做成VTuber，只是借用W0004「魯魯可以偶爾像活起來一樣講話」這個機制，放進一則貼文文案裡。

這個提案本身好不好可以再議，但重點是：**兩則各自獨立記錄多天前的素材，被重新組合出一個具體、今天就能拍的內容提案**——這就是v0.1要證明的第三件事。

**⚠️2026-09-23策提醒，避免誤讀**：這個demo證明的是「系統能組合出東西」這個技術能力，**不代表「兩個entry組起來」是未來的創意公式**，也不代表這個提案本身達到「我們要的驚喜品質」。組合出來的東西好不好、值不值得真的發，仍然要經過創意判斷（策/Grok/妹），倉庫只負責把散落的原料重新叫得出來，不負責替代創意判斷這一關。

## v0.1明確不做的事（留給v1+，不是漏做）

- 真正的向量/語意搜尋引擎
- 情境自動觸發機制（09-19規格裡的「反覆失敗→自動觸發擴大搜尋」這類主動性，v0.1靠CC自己記得檢查倉庫，不是系統自動跳出來提醒）
- 跨AI求救紀錄（誰解的/用什麼工具/成本多少）——先有東西可用，這層記帳之後再補
- 自動化淘汰執行——現在只是CC手動掃描時順便看一眼
