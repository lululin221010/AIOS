## 一、企劃階段：開工前質量關卡

**C提出新系列/新冊企劃時，CC先確認以下問題有答案，沒有就退回，不執行。**

### 開工前第0題（比原本3題更硬，2026-07-08最終版）
「這堂課有沒有一句話，是讀者自己問AI一次大概率不會得到、需要額外判斷或整理才寫得出來的？請直接寫出那句話。」——寫不出來，題目要重想，不要先開工。

### 原始3題（仍要回答）
1. 這冊有幾堂課？每堂的「核心概念」是什麼？（不是堂名，是真正能學到什麼）
2. 一個讀者讀完這冊，具體多懂了什麼？能做到什麼原本做不到的事？
3. 這冊的定價和市面免費資源比，差異化在哪裡？

### 冊數原則：先測獨立性，不硬拆
- 拆冊前先問：這幾冊拿掉順序，單獨一冊還能不能看懂、有沒有獨立價值？答案是「不行，一定要照順序讀才懂」→ 代表本質是一本書的章節，該合併不該硬拆
- 只有各冊主題可獨立成立（像理財書院入門/進階/高階，各自解決不同問題）才適合拆冊
- 堂數對應冊數：10堂以下→1冊；15~25堂→最多2冊；30堂以上→才考慮3冊
- 核心原則：**不硬拆，要精不要量**
- 已知白工案例（不要重蹈）：自律神經舊7冊，內容其實是一本書硬拆七冊，各冊高度連續依賴，2026-08-04已下架收回教訓；那個感覺36冊質量不足未上架

## 二、寫作階段：C自我檢查（單堂4項＋整本5項）

開工前3題只檔得住「企劃亂湊」，擋不住「執行階段品質不均」，需要逐堂自我檢查。

### 寫作中逐節自問（5項，C自己過）
```
□ 1. 可替換測試：主題詞換掉這段話還成不成立？成立=填充句，刪掉
□ 2. 具體到可能講錯的程度：有沒有數字/因果/情境，還是永遠正確的安全句？
□ 3. 角色是不是在做事：不能只是被提名字，情境要具體到有名字有數字有因果
□ 4. 結構完整：問題→機制性解釋→具體例子→限制或例外→可操作的判斷準則（五環節）
□ 5. 湊字歸因自問：這句話是這堂課需要，還是我需要湊字數？
```

### 字數雙向警訊
1500-2500字合理；低於1000字通常走不完論證閉環；**超過3000字通常是同一論點繞圈子，也是質量問題**（不是越長越好）。如果補強後多數堂仍卡在目標下緣，先檢查是不是切堂切得太細，不要繼續要求湊字（判斷訊號：整合收尾章把前面幾堂濃縮成更少節點，代表本來就該合併）。

### 交稿前紅燈訊號
這堂做出的具體判斷是什麼／如果只能留一段會留哪段（每段都差不多重要＝平鋪堆疊）／有沒有可能被讀者反駁的地方／讀完能不能一句話講出重點。

### 整本書要過5項
1. 每堂都過上面4項
2. 堂與堂之間有累積關係，不是各自獨立的知識點堆疊
3. 通過「讀者會不會覺得被騙」測試——深度要超過讀者自己問ChatGPT一次能得到的答案
4. 有適合的圖表（機械把關見下方「機械檢查」節）
5. 對應定價的份量門檻：抓實質內容字數是否合理（例如249元對應粗抓至少1.5萬字中文，依定價級距調整）

**核心原則：** 讀者付費買的不是「資訊」，是「別人已經幫他想清楚、組織好、做出判斷的思考路徑」。整堂課讀完找不到任何一句「這是作者的判斷、可能有人不同意」的話，就是不及格。

完整版（含4組合格/不合格對照範例）：[Content_Quality_Checklist.md](../05_Knowledge/Content_Quality_Checklist.md)——跨系列通用唯一權威版，新系列開工前直接丟給C。

### 免費堂規則
免費堂（試讀）必須是完整、正式的課程內容，**不是另外寫的縮減版或摘要稿**。付費解鎖後看到的其他堂也要同等完整度，不能因為顯示入口不同（好康書院 vs 真正書院頁）就縮水——兩處應直接複用同一份資料/同一個元件，不要維護兩份平行內容。

## 三、測驗品質雙項檢查（order bump前必跑）

課程系列被判定「內容加厚完工」後，**不能只看字數達標**，要跑這個檢查，兩項都過才能放心用在order bump（+99加購）模式：

1. **內容深度**：抽5~10題實際讀題目+四個選項+解析，判斷錯誤選項是不是「需要真的理解課程概念才能排除的合理誤解」，而不是一眼看穿的芭樂答案
2. **選項長度等長**：寫小腳本抓每題四個選項字數，算`max/min`比例。比例≥1.5就算有洩題風險，需要重寫成等長版本
3. **等長化本身也要驗收**：修正後除了看比例數字，還要抓「同一句話/高度相似句型是否重複出現在超過3題」（等長化偷懶會用公版填充句湊比例，跟內容灌水是同一種手法的變體）

修正方法：正解精簡、錯誤選項補足細節到接近長度，內容邏輯不能變。

## 四、大量重複性任務交派方法論（等長化/量產/去重類任務適用）

詳見[reference_codex_batch_pipeline_playbook_20260728]（ST repo memory），核心原則：
1. 先做小demo驗證方向對了，再決定要不要擴大規模
2. **拆成10~15筆一批交派，不要一次丟大量**——單一批次題數太多，Codex會發展公版句規避品質要求；小批次因為每批次都是全新context，反而逐題認真處理
3. Codex背景任務一律依序執行，絕不平行（平行會產生大量亂碼`?????`）
4. 派工前務必確認沒有其他聊天室同時在跑`codex exec`（CPU delta方法確認兩次閒置）
5. 無人值守管線：extract→codex exec→verify（自己寫腳本，不信自報）→merge→sanity_check，任何一步沒過立刻halt
6. 特殊/最後一批邊界，交派前先dry-run肉眼核對，不要相信手算的參數

## 五、技術上架注意事項

- MongoDB `digitalProducts`價格欄位一律用`priceTWD`，不要用`price`（股市三部曲當初用錯導致前端讀不到金額，已修正）
- 多系列書單頁面（好康書院、書院課程列表）系列數**4個以上**必須用tab摺疊顯示，預設只展開一個系列；系列數≤3可直接展開全部
- 一份內容如果要跨EPUB／互動課程／有聲書／短影音使用，格式規則見[內容母版MD規範.md](內容母版MD規範.md)

## 六、機械檢查（技術層，跟內容品質檢查分開做）

ST repo `pre-epub-check.mjs`負責格式面機械把關：圖片/格式/章節結構、CTA連結佔位符是否已解析（`[SD體驗URL]`這類殘留會被抓出來）、SELFCHECK標記格式對應的自動檢查。這一層跟C的內容品質自我檢查是不同層級，不要混在一起做。

## 七、三層分工總覽

- **C**：企劃階段第0題+3題、寫作中逐節自問5項、交稿前紅燈訊號——全部自己過一輪
- **GPT**（如有請它協助）：第二層——跨系列重複度檢查（不同系列會不會講到同一個案例）、邏輯連貫性、隨機抽節模擬讀者一句話測試
- **CC**：技術機械檢查（`pre-epub-check.mjs`）+ 測驗品質雙項檢查 + 大量重複性任務的Codex批次交派管理，跟內容品質檢查是不同層級

## 八、上架後維護

- 每個系列建議維護一份「現行使用版」快照資料夾，只放現行結果不放過程檔（規則見ST repo memory `feedback_current_use_folder_convention_20260727`），系列數≤3不分型態資料夾、≥4系列才分md/epub/課程三個子資料夾
- 內容/課程程式碼有異動時，主動重新整理對應快照，不用等提醒
