# 內容製作方法論：以「目標成品」反向搜尋製作捷徑

> 建立：2026-09-23，起因是「真人→AI即時易容／角色直播」這個具體案例討論後，妹明確指示這不是單次聊天素材，是SS／ST未來所有「內容製作」的長期工作原則，要求正式記錄進AIOS。
> **適用範圍**：跨產品線、跨內容格式（Reel、動畫、漫畫、角色影片、唱歌、直播、互動角色、圖像、短劇等），任何AI（CC／Co／C／SG）在啟動新的內容製作任務前都先套用本原則。

---

## 核心原則

**搜尋要以「我們想產生什麼內容效果」為起點，而不是以「我們手上有什麼工具」為起點。**

不要先從目前已知或已訂閱的工具開始做（例如「來，我們先寫prompt試Kling」）——這樣會永遠只在熟悉的工具圈裡打轉，錯過品質更好、更省力、或成本更低的現成捷徑。

## 固定流程

```
想做出的成品／效果
  → 搜尋目前全球已有的捷徑
  → 評估
  → 選最省力且品質達標的方法
  → 找不到合適捷徑才自行組工作流
```

## 「捷徑」搜尋範圍（不能只限App或主流AI模型）

必須包含：
- App／SaaS
- 外掛、插件、擴充功能
- 專用模型、LoRA
- ComfyUI節點與workflow
- GitHub開源專案、模板
- API／CLI、自動化
- 直播特效、後製工具
- 別人已驗證可複製的製作流程

## 評估時至少比較

最終品質、成功率、製作時間、金錢／token成本、人工操作量、Debug負擔、可重複性。

## 案例說明（不要把原則縮寫成案例本身）

2026-09-23討論「真人→AI即時易容／角色直播」時，原本的反射動作是「先寫prompt試Kling」，直接從已知工具出發。經妹糾正後，正確流程應該是：先定義「想做出的成品」（即時、可互動、角色臉／聲音替換的直播效果）→ 搜尋全球現有的即時換臉/换聲直播捷徑（例如專用即時換臉App、OBS外掛、直播特效工具等）→ 評估這些捷徑跟自建workflow的成功率／品質／成本／人工負擔 → 選最省力的方案。

**這個案例只是本原則的第一個應用例子，不代表本原則等於「換臉或直播研究」——下次遇到動畫、漫畫、唱歌、短劇等任何新內容形式，都要重新走一次同樣的搜尋流程，不能假設上次找到的捷徑這次也適用。**
