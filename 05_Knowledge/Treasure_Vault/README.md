# 寶庫（Treasure Vault）

> 建立日期：2026-08-28
> 建立起因：妹反映「一次整理全部」的工作方式行不通，改成流水式——想到一顆就交一顆，CC 隨到隨建檔，不等「盤點完成」。

## 用途

保存妹平常從 IG／Threads／YouTube／X／網站，以及與 GPT/C/CC 工作過程中發現的 AI 工具、技巧、商業案例、工作流與市場情報。

**這不是 Prompt Library。** [Prompt Library](../Prompt_Library.md)（`01_Company/AI_Team_Roles.md` 定義，目前尚未建立內容）只保存「實際驗證有效的 Prompt」。寶庫是更廣的情報與可再利用資產庫，涵蓋工具、技巧、案例、市場訊號，不限於 Prompt。兩者分開維護，不合併。

## 資料位置

- 正式資料：[Treasure_Vault.md](Treasure_Vault.md) — 索引表 + 完整寶物卡
- 目前規模：B001～B030（2026-08-28 首批建檔，來源為 GPT 回填）

## 建庫原則

1. 一顆寶只有一筆主紀錄，以多標籤處理，不因同時屬於「AI寶＋創業寶」而複製兩份。
2. 原始網址盡量保存；來源失效也不刪紀錄。
3. 「別人影片聲稱」與「我們實測確認」必須分開標註，不可混為一談。
4. 寶物會零星交付，不等待完整盤點；收到一筆就入一筆，直接 append 到 `Treasure_Vault.md`。
5. 寶庫需能依分類、標籤、驗證狀態、Lulu/SS/ST 用途搜尋——目前用 Ctrl+F／grep 查 markdown，量大之後再評估要不要換資料庫實作，但欄位資訊不因實作方式改變而遺失。
6. 不因建寶庫本身新增 SS/ST 功能或改網站；這只是 AIOS 情報資產維護。
7. 若寶物與 AIOS 現有資料／Decision Log 有重複或衝突，先指出，不直接覆蓋。
8. 殘缺資料（沒有原始網址／作者／完整細節）一律誠實標「待補」，不得為了好看而編造。

## 新增寶物的標準流程

1. 妹或 GPT 提供寶物卡（可以只有 1 顆，格式照上面欄位）。
2. CC 讀 `Treasure_Vault.md`，確認 ID 不重複（依現有最大編號 +1，格式 `B0XX`）。
3. 補進索引表 + 完整卡片，缺欄位一律標「待補」/「待判斷」，不臆測。
4. 若牽涉 AIOS 既有決策（如 Lulu 視覺系統第三套提案 B017），在卡片備註標明「需妹正式拍板」，不擅自覆蓋既有規格。
5. 這屬於「資料 update／記錄維護類工作」，直接做完再通知，不用每次先問「同意嗎」。

## 加工鏈（見 B015／B030）

外部情報 → 查證 → 寶物入庫 → 實測 → 形成技巧 → Lulu 社群素材 / SS 免費內容 / 內部工作流改善 → 跨寶市場訊號 → 商機候選。不是每顆寶都要強推成商品，只有多顆寶反覆指向同一痛點才升級討論。

## 建檔完成 ≠ 用完了：下一步進候選池（2026-08-29新增）

寶庫只回答「我們有什麼好東西」，不負責「接下來去哪裡、什麼時候用」——這是另一份文件 [Content_Candidate_Pool.md](../Content_Candidate_Pool.md) 的責任，不要混在寶物卡裡處理。

**新卡片建檔時的機械規則**：若卡片「可變 Lulu／可變 SS／可變 ST」任一欄位標「是」或「可能」，CC 順手在 `Content_Candidate_Pool.md` 加一行（來源連結回本寶物 ID），狀態預設 `WAITING`。**CC 不自行判斷觸發條件、優先度、值不值得做**——這是內容品質／商業判斷，屬 GPT／妹的責任（見 `01_Company/AI_Team_Roles.md`「CC 不介入 editorial 判斷」）。CC 只確保「這顆寶有沒有被登記進候選池」這件事不漏掉，不做「這顆寶該不該做」的判斷。

三層不要混：Treasure Vault（有什麼）／Content_Candidate_Pool（可能去哪、要不要做）／各專案 Tasks.md（現在真的要做）。Buffer Ideas 只接候選池裡已判斷「確定要做成社群內容」的項目，不是全公司候選池。
